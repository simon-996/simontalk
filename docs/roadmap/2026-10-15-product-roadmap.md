# SimonTalk 产品建设路线

日期：2026-10-15。目标：逐步交付本人和少量朋友可以长期使用的英语口语产品。

本路线明确推进顺序、阶段产物和完成标准。实际进度和当前工作边界由根目录 HANDOFF.md 维护；编写路线不代表已经授权所有后续付费试验或发布。需求与选型状态仍以[产品总纲](../superpowers/specs/2026-10-15-simontalk-mvp-design.md)为准。

AI 交接先读根目录 [AGENTS.md](../../AGENTS.md) 和 [HANDOFF.md](../../HANDOFF.md)。本路线定义各阶段的目标与完成标准；最新进度、下一步和工作边界集中在 HANDOFF.md 更新。

## 1. 推进原则

- 每个阶段完成一组能验证的能力，并接入后续正式产品；示例数据只用于测试和预览，不充当真实练习结果。
- 优先解决自然语音的关键不确定性。先建立够用的工程和界面基础，尽早验证真实音频，再扩大业务范围。
- 身份隔离、异常处理、媒体释放、基础用量记录和可访问性随相应功能一起交付。后续集中验收继续加强这些能力。
- 保持一个 GitHub 仓库，使用 main 主分支；客户端、后端和部署按需独立发布。每个实现阶段形成可追溯的提交和验证记录。
- 阶段完成由运行结果决定；文档维护方案、验收证据和剩余限制，不以页面数量衡量进度。
- 每阶段开始时再拆分具体实施任务，防止模型选型或实测结果变化后，大量远期实现步骤失效。本文不承担逐文件代码实施计划的职责。

## 2. 七个阶段

| 阶段 | 用户能得到什么 | 主要交付物 | 完成标准 |
| --- | --- | --- | --- |
| 1 方案收敛与开发准备 | 清楚知道做什么、采用什么方案、如何判断完成 | 产品范围、技术决策、视觉规范、设备与账号条件、试验费用边界 | 自有系统关键选择收敛；外部能力有明确验证方法；首个开发阶段具备可执行输入 |
| 2 工程底座与组件系统 | 可以进入自己的账号，看到一致、可操作的应用基础 | Flutter 三端工程、业务后端和数据库、认证、主题和基础组件、自动检查 | 干净环境可按文档启动；三端可构建；账号隔离有效；加载、空态、失败和大字号可用 |
| 3 真实语音练习 | 能和 AI 连续聊英语、自然插话并结束 | 鉴权建连、音频适配、状态、静音、插话、最终转写、结束与基础计量 | 使用真实服务和设备验证接话、停顿、回声、插话与释放；能解释一次练习的实际用量 |
| 4 完整学习闭环 | 选择话题、获得辅助、看复盘、重练并回看记录 | 独立难度、话题、提示和翻译、会后反馈、关联重练、历史与删除 | 完整流程使用真实数据；反馈可定位实际原话；重练不覆盖原练习；异步任务和提交可恢复 |
| 5 可靠性与成本控制验收 | 失败可恢复，个人内容和费用有可靠边界 | 故障演练、权限验证、用量对账、终止控制、备份恢复与删除检查 | 关键失败场景有结果；费用控制能力有证据；备份能恢复并重放删除；无跨用户访问或数据复活 |
| 6 三端交付与朋友试用 | 本人和朋友可以在各自实际设备上独立使用 | HTTPS Web、手机分发版本、环境配置、运行监测、试用记录与修复 | 核心流程在支持矩阵内走通；发布可回退；不同水平用户独立完成练习；高影响缺陷解决 |
| 7 持续使用与成熟维护 | 长期练习时自然、可信、稳定，并能持续改善 | 基于真实使用的体验优化、稳定发布流程、运行手册、按需增加学习积累 | 有持续使用证据；体验、反馈、数据、费用和运维均达到成熟标准；新增功能有实际需求和验收依据 |

第 3 阶段形成真实可说的语音能力；第 4 阶段形成首个完整练习版本；第 6 阶段形成朋友可稳定试用的交付版本。第 7 阶段通过持续使用和维护积累成熟度。

## 3. 各阶段的关键边界

### 阶段 1：方案收敛与开发准备

本阶段收敛产品、页面、视觉、技术与验证规格，准备必要的工具、skills 和仓库。以下工作在进入对应开发前落实，实际完成情况见交接文档：

1. 将客户端状态/路由、后端、数据库、访问方式及数据策略从建议收敛为具体决策，保留依据与日期。
2. 确定首批实际设备和系统版本、主力使用端及三端验证顺序。
3. 核对工具链、可用模型账号、地域与权限，明确试验允许的费用范围。
4. 统一规格中的视觉角色、操作语义和数据行为；未来供应商能力由阶段 3 实测决定。

普通工程细节按既定规范推进。设备、账号权限、可接受费用和确实影响产品行为的取舍，在需要时集中确认，不把每个按钮尺寸都变成单独的许可请求。

### 阶段 2：工程底座与组件系统

按仓库约定建立 apps/client/、services/api/ 和 deploy/ 的必要内容。完成配置读取、数据库迁移、认证和最小健康检查；供应商长期密钥只由服务端持有。

把视觉规范落实为共享主题及按钮、输入、状态提示、导航、话语、反馈条目和伙伴组件，预览覆盖深浅色、大字号和异常。首批页面包含访问、主页与个人设置；通话相关组件预览使用明确的测试状态。

建立有用的格式、静态分析、核心测试和构建检查，记录本地运行方法。此阶段的构建成功只证明工程可构建，不作为真实语音或学习效果的证据。

### 阶段 3：真实语音练习

使用真实服务完成“本人开始 → 授权 → 建连 → 连续交流 → 自然插话 → 结束 → 查看最终文字和用量”。先集中验证主力设备和 Web，随后在同阶段补齐另一手机端的关键音频路径；避免业务做完后才发现平台音频不成立。

按[验证计划](../validation/2026-10-15-validation-plan.md)观察基础用户的停顿、外放回声、自然插话、旧回复取消、实际播放上下文、断线和后台暂停。界面显示对应真实媒体状态，明确本地停止和上游终止的区别。

产出供应商、模型、地域、协议、能力和实际费用的选型记录。当前千问 WebRTC 路线是首轮候选；不能满足关键要求时，依据失败证据评估受控 RTC 或服务端持有上游连接的方案。阶段结果必须明确强制结束与硬额度是否可信；需要硬上限时，缺失该能力的路线不能通过相应准入。

### 阶段 4：完整学习闭环

补齐自由聊天与日常话题、个人难度、英文字幕、中文提示和按需辅助。完成会后反馈、逐句重练、记录详情与级联删除。

反馈保存真实引用、输入版本和建议类型，允许零至三项，不输出无音频评测支持的发音分数。重练拥有自己的身份、转写和用量，同时能返回来源复盘。通过持久任务、幂等提交与平台补交策略处理保存、反馈失败和进程重启。

阶段验收至少覆盖：正常结束、内容不足、无可靠转写、反馈失败重试、两次独立重练、重复结束、删除原练习及晚到结果。形成完整体验后，再扩大试用覆盖。

### 阶段 5：可靠性与成本控制验收

集中验证断网、业务后端失联、供应商超时、设备切换、锁屏、应用被杀、并发启动和重复事件。检查历史设置快照、跨账号访问、退出清理与删除后晚到结果。

对照供应商账单检查语音、反馈、辅助与重练用量，区分估算、客户端观测和可信结算。验证准入、并发及已建媒体会话的终止机制；未能证明的硬费用上限如实记录，并完成是否接受相应试用边界的决定。

进行数据库备份恢复、删除清单重放和失败任务恢复演练。产物包含复现步骤、证据、修复与复测结果；遗留限制反映在界面、支持范围和运行说明中。

### 阶段 6：三端交付与朋友试用

完成 Web 的 HTTPS、前后端环境配置、数据库迁移与部署流程，以及目标手机的签名、构建和合适的分发方式。先服务受邀使用者；面向公众或商店的发布范围与要求在决定公开发行时另行确认。

在真实大陆 Wi-Fi、移动数据、外放和常用耳机上跑通完整流程。部署具备健康状态、脱敏错误和用量观察，并完成一次可执行的回退验证。

让不同水平的实际使用者独立进入、完成练习并查看复盘。重点收集抢话、听不懂、不会求助、反馈不准确、恢复困难和内容丢失，而不只收集配色喜好。所有问题按影响排序，保留修复后的复测结果。

### 阶段 7：持续使用与成熟维护

先根据实际对话改善接话、等待、语速、追问和反馈，消除重复出现的使用障碍。功能扩展依据真实需求逐项进入，不为增加页面数量引入完整课程、社交或人物系统。

学习积累可按需从“保存有价值的表达、复习常见问题、跟踪练习历史”中选择最有效的一项；它们对应总纲后续需求 R13，不自动变成当前版本全部必交功能。专项发音评测 R14、丰富人物与激励 R15 仍单独选型和验收。

维护工作包含依赖升级、数据库迁移、备份检查、费用趋势、问题定位和版本回退。持续使用记录建议跨越至少两周，覆盖日常使用与异常恢复；时间跨度仅是观察起点，不能单独证明体验成熟或学习有效。

## 4. 成熟标准

| 维度 | 可检查的依据 |
| --- | --- |
| 使用价值 | 不同水平用户能够独立开始、聊完、理解反馈并重练，实际使用中能指出收获与问题 |
| 语音体验 | 支持的设备与网络有实测记录，接话、停顿、插话和回声达到已确定目标；没有用平均值隐藏失败 |
| 反馈可信 | 抽查可以定位原话、核实解释和原意；不凑错误数量，不把可选润色当成错误 |
| 数据可靠 | 账号隔离、幂等、版本、重启恢复、备份恢复及删除演练通过，无已知数据泄露或内容复活问题 |
| 费用清楚 | 实际用量能核对，准入和终止能力有证据，费用异常可以定位；对未结算信息有明确状态 |
| 交付稳定 | 支持矩阵清楚、主要流程可回归、发布和回退可执行，有运行说明和真实缺陷记录 |
| 维护可持续 | 一个人可以依照文档更新、部署、恢复和排查，架构复杂度与小范围使用匹配 |

跨用户访问、用户结束后仍未受控拾音、不可恢复的主要记录丢失、关键设备无法完成语音或无法解释的持续费用，均属于需要优先解决的问题，不能在未明确限制和处理的情况下称为成熟版本。

## 5. 与现有验收关卡的对应

| 现有关卡 | 对应阶段 | 说明 |
| --- | --- | --- |
| G0 文档一致性 | 阶段 1，并贯穿后续变更 | 保持需求、交互、视觉、接口和数据规则一致 |
| G1 开发准备 | 阶段 1–2 | 明确设备、工具链、账号与费用输入，工程能够运行 |
| G2 语音候选 | 阶段 3 | 尽早验证真实语音及供应商选择 |
| G3 完整练习 | 阶段 4–5 | 业务闭环与系统性可靠性验收 |
| G4 小范围试用 | 阶段 6–7 | 真实使用、修复和持续优化 |

R01 的身份基础在阶段 2 完成；R02–R06 的语音、难度、话题与辅助在阶段 3–4 完成；R07–R09 的反馈、重练和记录在阶段 4 完成；R10–R12 的恢复、三端与用量从相关能力开始时实现，在阶段 5–6 扩大覆盖并集中验收。

## 6. 进度与排期方式

当前阶段、已完成能力、验证证据、剩余事项和下一步统一在根目录 HANDOFF.md 维护。本路线保留阶段定义，避免在多个文件复制即时进度。

后续每次汇报说明四件事：本次完成的能力、实际运行或检查结果、剩余问题、下一次具体交付。每阶段结束更新证据与状态，再拆下一阶段的实施任务。

详细工期在阶段 1 明确投入和设备条件、阶段 3 获得语音基线后逐步校准。当前不预设一个缺少实际开发速度、模型表现和试用证据的总完成日期。
