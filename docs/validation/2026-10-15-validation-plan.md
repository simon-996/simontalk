# SimonTalk 验证与验收计划

版本：验证与验收规格 · 2026-10-15。指标中的暂定目标及尚未执行的项目分别标明。

本文件定义开发和试用时的验证方法。执行进度与证据见根目录 [HANDOFF.md](../../HANDOFF.md) 及各次验证报告，不能把下列计划当成已经执行的结果。

产品范围与决策状态以[产品总纲](../superpowers/specs/2026-10-15-simontalk-mvp-design.md)为准；页面和技术行为分别见[交互规格](../design/2026-10-15-screen-and-interaction-spec.md)、[技术设计](../architecture/2026-10-15-technical-design.md)。

视觉规范中的色板、文字层级、响应式、组件状态和预览矩阵见[视觉设计规范](../design/2026-10-15-visual-design-spec.md)。组件预览及色值计算用于视觉检查，不替代三端真实语音和可访问性验证。

## 1. 验证要解决的五个问题

1. 中国大陆的实际网络能否支持自然英文交流。
2. 系统能否区分用户在思考、真正说完、插话与背景噪声。
3. iOS、Android、Web 的权限、外放、耳机与恢复行为是否一致可理解。
4. 转写、反馈、重练和个人记录能否可靠保存，并彼此隔离。
5. 能否解释真实用量，并通过可信机制控制费用，而非只在界面显示额度。

供应商的单项功能列表、开源项目的 README、脚本演示和文字流式输出都不足以单独回答这些问题。

## 2. 评审与验证关卡

| 关卡 | 输入 | 产物 | 通过依据 |
| --- | --- | --- | --- |
| G0 文档一致性 | 产品、交互、技术和本计划 | 决策登记和相互一致的规则 | 已确认项与建议分清，关键状态和数据行为无矛盾 |
| G1 开发准备 | 目标设备、可用工具链、服务账号、试验预算 | 环境和开通条件清单 | 能解释准备工作和允许试验的边界；预算未明确时只做不产生模型费用的检查 |
| G2 语音候选 | 可用模型和当前Web支持范围内的最小语音路径；原生恢复时补验 | 原始记录、失败样例、质量与用量结果 | 覆盖实际网络、停顿、插话、回声、设备变化及服务端结束能力 |
| G3 完整练习 | 身份、语音、转写、反馈、重练、历史 | 端到端结果与缺陷记录 | 核心流程完整，权限与数据正确，异常可恢复 |
| G4 小范围试用 | 通过前述关卡的版本 | 真实用户反馈及优先级 | 多个水平用户能独立完成练习，关键缺陷已处理或明确限制 |

若需改变体验目标、后台策略或媒体架构，先更新总纲决策状态及受影响文档，再继续对应验证。

## 3. 设备与网络矩阵

2026-10-16用户更新为Flutter Web优先，暂停原生构建与安装。下表按当前Web范围执行；没有实测的平台不列为已支持，也不以原生设备条件阻塞Web开发。

| 维度 | 至少覆盖 |
| --- | --- |
| 手机 App | 当前暂停；恢复时验证实际试用者的iPhone和Android真机，模拟器只辅助 |
| 手机浏览器 | 先验证Android Chrome的Web入口；iPhone Safari纳入支持范围前补验 |
| 桌面 Web | 一个 Chromium 浏览器；目标用户使用桌面 Safari 时增加该项 |
| 网络 | 中国大陆 Wi-Fi、移动数据；至少包含两种不同接入环境 |
| 音频 | 手机外放、常用蓝牙耳机；实际用户使用有线耳机时增加该项 |
| 用户表达 | 开口困难、能简单交流、较熟练；有口音、短停顿、长停顿与自我修正 |
| 生命周期 | 首次授权、拒绝后重试、设备变化、临时断网、切后台/锁屏、返回前台、结束 |
| 外部失败 | 供应商拒绝、超时、额度不足、业务后端失联、反馈调用失败 |

受支持的最低 OS/浏览器版本应根据实际设备和 Flutter/媒体依赖兼容性形成一份版本矩阵。没有测试的组合明确标为未验证。

## 4. 指标定义与暂定体验目标

下面是用于首轮原型的工程目标建议，尚非用户确认的服务承诺。获得真实基线后，记录是否维持或调整；不能因为候选方案表现差就默默改动定义。

| 指标 | 计量定义 | 首轮目标建议 |
| --- | --- | --- |
| 建连成功 | 用户开始后，麦克风和双向媒体真正可用 | 正常网络每个平台至少 10 次启动；逐次记录成功与失败，首轮目标为至少 9 次成功 |
| 接话时间 | 最后有效用户语音结束到首次实际播放 AI 声音，包含判停等待 | 明确完整句场景：P50 ≤ 2.5 秒、P95 ≤ 5 秒 |
| 插话停止时间 | 用户有效插话开始到旧 AI 音频停止播放 | P95 ≤ 500 毫秒；同时核查上游取消与上下文截断 |
| 抢话 | 语义尚未完成、用户仍准备继续时 AI 开始回答 | 带标注停顿场景中误判率 ≤ 10% |
| 误打断 | 背景声或 AI 自身回声导致旧回复被取消 | 已标注无有效插话的场景中误触发率 ≤ 5% |
| 结束后释放 | 用户确认结束到本地麦克风/播报与连接释放 | 本地资源在 1 秒内释放；供应商实际终止和费用停止另行验证 |
| 反馈可用性 | 生成成功、结构完整、引用存在、内容有依据 | 所有试用反馈均可追溯原话；失败可重试，不凑数量 |
| 记录完整性 | 原会话、最终话语、反馈与重练关系一致 | 重复保存不重复，开始新练习不覆盖旧记录，删除遵循关联规则 |

初轮每个平台至少采集 30 个有效轮次，用于暴露明显问题；样本小于 100 时，P95 仅作方向观察，报告中附样本量，不能声称尾部延迟已稳定。

失败轮次单列数量、原因和等待时间，不从成功率或体验报告里消失。不同网络、平台、外放/耳机和水平分组报告；不能把所有数据混成一个平均数掩盖特定场景问题。

接话测试和停顿测试分开：不能通过迫使初学者在短时间内说完来取得漂亮的接话指标，也不能靠让所有人长时间等待来消除抢话。

## 5. 语音场景清单

| 场景 | 操作与输入 | 观察要点 |
| --- | --- | --- |
| 完整短句 | 清楚说完一句日常英语 | 接话时间、字幕与语义 |
| 组织句子 | 在句子中间停顿约 1、2、3 秒后继续 | 是否过早结束、碎片转写、抢话 |
| 自我修正 | “I go… I went there yesterday.” | 是否保存正确最终意思，反馈是否误判 |
| 语音插话 | AI 播报时直接开口，不先点击按钮 | 停止旧音频、取消旧回复、后续对话不混乱 |
| 点击插话 | AI 播报时点击“我来说” | 与语音插话状态一致，仍可继续拾音 |
| 回声 | 外放且不说话，再与耳机对比 | AI 自身声音是否被当成用户发言 |
| 背景噪声 | 有音乐或其他人说话的典型环境 | 误打断、乱转写、是否需要说明限制 |
| 中英混合求助 | “这个词怎么说？I mean…” | 请求帮助与日常英语对话能否自然衔接 |
| 断线 | 说话或播放时短暂断网，再恢复 | 暂停提示、旧音频处理、重新连接与上下文恢复 |
| 后端失联 | 媒体仍连接时让业务请求不可达 | 是否仍在计费、最终话语能否补交、强制额度是否真实可执行 |
| 后台/锁屏 | 按建议策略暂停后再返回 | 停止拾音、明确恢复动作、不假装无缝续接 |
| 设备切换 | 连接/断开耳机与切扬声器 | 声音路径、回声、状态和用户理解 |
| 无有效内容 | 不说话、只有噪声或连接失败后结束 | 不生成虚构错误或成绩，保留可理解的结束结果 |
| 结束边界 | 用户在 AI 说话时结束 | 不再播报、不会旧会话继续拾音或重复计量 |

## 6. 业务与数据验收清单

| 对应需求 | 验证方式 |
| --- | --- |
| R01 身份 | 用户 A/B 隔离；替换资源 ID；未登录/过期身份；邀请码过期、撤销和重复使用 |
| R02 设置 | 修改难度后新会话变化；旧会话保留难度快照；不同账号不共享设置 |
| R03–R06 练习 | 自由聊和话题入口；权限被拒；字幕与中文辅助独立；主动求助与集中纠错区别清楚；提示/翻译不冒充用户原话，展开结果不重复计费；当次“说慢一点”与个人默认语速分开 |
| R07 反馈 | 原话不存在、转写不清、内容不足、无明显错误、模型格式错误与超时 |
| R08 重练 | 正确关联原表达；独立用量；返回原复盘；重练失败不破坏原记录 |
| R09 历史 | 多次练习均保留；列表与详情一致；重复最终话语不产生重复；中断记录可区分 |
| R09 删除 | 删除原练习及关联反馈、辅助文字、未完成任务和派生重练；删除单次重练不影响原练习；用量账本不含原话 |
| R10 恢复 | 反馈任务重试、重复结束、进程重启后的未完成任务、重复供应商事件 |
| R11 界面 | 窄屏/桌面、深浅色、键盘导航、屏幕阅读器标签、触控目标、错误态不遮挡主操作 |
| R12 用量 | 同时启动两次、旧会话未释放、供应商用量迟到、客户端提前离开、前端计时被绕过 |

反馈质量由人工抽查实际对话：说明是否准确、是否真有必要、是否易懂、是否能重练。不能用“模型返回了合法结构”替代反馈正确性。

## 7. 记录字段与证据

每次实验建议记录：

- 构建标识、平台/OS/浏览器、网络、音频设备、难度与场景。
- 供应商、地域、模型、语音配置与接话策略版本。
- 会话/轮次 ID、各阶段时间戳、实际播报开始/停止、最后确认的用户语音结束。
- 是否发生抢话、误打断、漏转写、旧音频残留与恢复失败。
- 供应商事件与用量信息、业务结束和媒体结束是否一致。
- 重现步骤和缺陷结论，明确观察事实与推断。

日志使用内部 ID，去除密钥、密码和完整身份凭证。日常运行默认不保存原始用户音频。若验证插话时间需要录制测试音频或视频，单独约定测试素材、用途、参与者和清理方式；该约定不自动扩大为保存所有用户会话。

## 8. 成本验证与强制额度

先核实供应商的计费口径：输入/输出音频、文本、连接时长、静音、RTC、重练和失败调用分别如何计费。有效说话分钟和连接分钟不能混用。

对每次实验列出实际计量单位、数量、单价来源与金额。总成本按各项目“实际用量 × 对应单价”求和，再单列必要基础设施费用。报告每次五分钟练习、每位试用者每日练习和不同输入假设下的结果；价格以实际账号地域和可用模型为准，不预填未经核实的金额。

强制额度验收需要证明：

1. 后端能限制新会话与并发，重复请求不会绕过。
2. 旧媒体连接不会因业务失联而无限继续消耗。
3. 供应商可信会话时限或服务端终止方式有效，普通客户端不能撤销该限制。
4. 结束事件和用量迟到时仍可核对，不因用户删除记录而退还额度。

缺少第 2–3 项证据时，只能称为启动限制或软额度；应评估服务端持有上游连接或受控 RTC 路线，不能以界面倒计时宣称已经控制费用。

## 9. 报告格式与下一步决定

每轮验证交付一份报告，包含：配置和样本、覆盖矩阵、逐场景结果、延迟分布、失败与未验证组合、实际用量与费用、建议继续或调整的原因。

语音路线通过后，再推进完整账号和记录闭环；若未通过，保持产品需求不变，明确问题出在模型、媒体、接话策略、设备还是网络，再对候选做有针对性的调整。

验证按建设路线、实际准备条件和最新用户授权执行；当前允许开展的工作以根目录 HANDOFF.md 为准。
