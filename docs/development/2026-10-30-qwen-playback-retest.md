# 千问 WebRTC 播放受控复测

2026-10-30，使用 macOS Edge、真实北京千问信令网关、仓库生产 `realtime_transport.js` 和本机静音合成输入；没有申请或使用物理麦克风。每次启动的探针服务最多一次 SDP 交换，共启动三次，没有自动重试。生产传输脚本 SHA-256 为 `17bef89ce4a62acbcc8557464f9514656d411694b8d91366585eea949bad13e5`。

## 实际过程与边界

1. 原探针首次收到真实交换成功、配置更新、回复请求及 `response.done`，但把生产传输的 `(code, detail)` 两个字符串误当作一个对象，观察记录显示 `undefined`，收尾计数抛错，证据未写入。关闭实验标签及本机服务后结束本地连接，不能据此确认上游已释放。检查发现旧探针**没有将输出元素设置为静音**，与原工具说明不符：这次是否产生可听输出未知。没有记录回复状态、usage 或音频数据，费用未知。
2. 修复事件参数、实际静音及先释放媒体再写证据后，第二次观察到 `playback_playing`，但事件发生在 `response.created` 之前。旧探针因此过早收尾，未收到 `response.done`；保留[原始证据](evidence/2026-10-30-qwen-playback-probe-early-playing.json)。输出元素已设静音，费用及远端释放仍未知。
3. 修复过早收尾并加入 `response.done` 时的入站 RTP 音频字节统计后，第三次得到一次交换、`session.created`/`session.updated`、一次回复请求和 `response.done`；本地播放器报告 `playing` 1 次、`waiting` 0 次、`failed` 0 次。回复终态事件到达时 WebRTC 统计入站音频 **22,933 字节**；两秒后本地停止，证据 POST 返回 204。见[原始证据](evidence/2026-10-30-qwen-playback-probe.json)。输出元素静音；本次没有保留回复状态或 usage，费用和上游释放未知。

第三次的 `playing` 早于 `response.created`，入站 RTP 字节数也不区分静音与模型语音。因此这次只能证明播放器进入 `playing` 状态且连接收到了入站音频，不能证明模型回复已经播出、实际人耳听见、文本与音频对齐或可信退出；也不是产品页面、真实麦克风、多轮或插话验收。不得据此开放正式语音准入。三次调用的实际费用以供应商账单为准，不能把未记录的 usage 当零。

## 探针修复与验证

- 生产回调按 `(code, detail)` 记录；实际创建的音频元素设为静音，结束时恢复临时替换的浏览器方法。
- 不再以早于模型回复的 `playing` 为终点；等待 `response.done` 后两秒结束，45 秒总计时从点击开始。终止媒体先于证据网络写入，写入失败也不阻挡释放；RTP 只记录音频入站字节总数。
- 新增页面 JavaScript 行为回归，先复现旧版 `startsWith` 异常和过早结束，再修复；覆盖静音、真实回调形状、响应终态、字节计数以及证据写入失败时的本地释放。
- `uv run --project services/api pytest services/api/tests/test_qwen_playback_probe.py -q`：6 项通过；目标文件 Ruff 和格式检查通过。未重跑客户端、后端全量或 Web 构建，因为生产传输与应用代码未改。
- 三次实验标签和本机服务均已关闭；本地关闭不是供应商端计费结束证明。下一步要验证真实回复音频到输出设备、播放边界/自然插话与可信上游退出，再考虑准入及真机验收。
