# 千问受限实时协议候选验证

日期：2026-10-29。此报告保留当时的实验和门禁结果；2026-10-30供应商答复后工具配置门已调整并实测，见[新报告](2026-10-30-qwen-reply-and-webrtc-verification.md)。正式语音准入仍关闭，真实通话功能未完成。

## 实现与边界

新增 `QwenGuardedProtocol`，仅接受北京地域千问 3.8 实时型号。候选实例绑定单事件通道，先要求供应商回显请求配置，再允许控制器激活媒体；单个用户语音项的最终识别到达后只请求一次回复，第二次发言及异常事件触发安全停止。回复文字复用归一化器和实际对话投影，播放状态保持 unknown。收尾时禁止新回复；已绑定的在途回复最多请求一次取消。用户最终文字和已绑定助手项的有限迟到最终文字可作为收尾尾部。

候选仅用于测试显式构造，没有注册为正式提供商。它不提供播放前缀、可靠上下文截断或可信远端退出；特别是回复请求已发送但 `response.created` 晚于收尾的情况，尚不能确认上游已停止。一次交互限制也不满足自然多轮对话与插话需求。

## 实际供应商观察

1. 第一次单次 WebSocket 会话，使用固定合成语音，完整输入、一次明确请求的回复及 `response.done` completed；收到 165,120 字节音频，仅计数未保存。识别和回复事件脱敏成[39 条有序记录](../../apps/client/test/fixtures/qwen_guarded_synthetic_events.json)，用量及摘要见[证据](evidence/2026-10-29-qwen-guarded-live.json)。此次观察记录了当时要求的配置字段，没有记录 `tools` 与 `enable_search`，不能证明它们的值。返回用量按当时标价估约 0.001827 元，实际结算及未返回费用未知。
2. 收紧配置后第二次 WebSocket 只发送会话配置，不上传音频、不请求回复；严格回显检查报告 `tools` 不匹配并关闭连接。
3. 第三次仅配置的 WebSocket 专门区分字段缺失和空值：成功收到 `session.updated`，`enable_search` 为 false，而 `tools` 字段不存在；没有上传音频或请求回复。两次的脱敏结果见[配置观察](evidence/2026-10-29-qwen-guarded-config-observations.json)。

三次连接均无自动重试，均观察到双方 1000 关闭帧。关闭帧和成功响应都不能证明服务端资源已释放或费用已结算。第二、三次无模型回复用量回报，不将未知实际费用记为零；累计实测仍须纳入用户已授权的 20 元上限，估价不构成硬停费。

[供应商服务端事件文档](https://help.aliyun.com/en/model-studio/server-events)称 `session.updated` 表示配置请求成功；目前没有获得足够证据说明该字段缺失一定等价于空工具列表，因此候选仍要求实际回显空列表并对当前真实回包失败封闭。不能将第一次较宽松的成功视为当前严格候选可实际接入的证明。

## 本地验证和下一步

真实脱敏记录直接回放在配置门处拒绝；另一测试只在内存中给该记录补上模拟的 `enable_search:false` 和空工具字段，用以测试其余事件处理，并非实测回包。覆盖搜索启用、非空/缺失/null 工具、配置差异、不同通道、用户项错配、空转写、意外回复、重复输入、停止时重入以及取消次数；另用真实媒体控制器配替身传输验证配置门和后续停止。目标测试15项通过；最终 Flutter 全量1469项通过、10项专用夹具跳过，静态分析、229个 Dart 文件格式检查及 Web release 构建通过（编译55.1秒）。

继续从公开契约或可复现且有边界的证据确认空工具配置语义，评估能否安全接入；之后仍须解决可信上游终止及费用、可证实播放前缀与上下文截断，并完成 WebRTC/真实设备验证。当时供应商询问草稿尚未发送；用户随后授权联系并已转述答复，见新报告。

## 收尾顺序修补（后续继续）

复现：语音项刚开始后立即收尾，旧实现会将未观察到对应停止和提交的最终转写发布到投影；真实媒体控制器会接纳冻结项的该最终文字。原因是收尾分支只匹配 item ID，没有复用激活期间的停止及提交资格，且忽略了收尾后迟到的停止与提交。两条回归先按预期失败；修复后仅按原项依次接纳停止、提交及最终文字，其他项或先提交后停止均不能建立资格。额外覆盖停止发生在收尾前、提交和最终文字发生在收尾后；真实控制器配替身传输的组合测试验证提前 final 不入投影、合法尾部入投影且不发送新回复。目标21项通过，Flutter全量1475项通过、10项专用夹具跳过；分析、229个Dart文件格式及Web release构建通过（编译42.6秒）。该证据来自本地替身，不证明真实供应商或设备行为。

## 回复创建迟到的处理

构造真实控制器配替身传输场景：已发 `response.create` 后用户结束，`response.created` 在协议进入收尾后到达。旧实现忽略该事件，控制器继续停留在 draining；协议级与控制器级用例先分别失败。现对收尾时出现的未知回复立即失败封闭，控制器停止本地传输，不发布新助手话轮、不发送未获冻结授权的取消；保留释放状态 unconfirmed。原回复已绑定时，仅相同 ID 的重复创建事件可忽略，其他 ID 或异常结构关闭。

另测 `response.created` 在传输 `beginDrain` 同步回调中到达：此时协议尚未进入收尾，但控制器已冻结范围；控制器拒绝对未冻结响应发送取消并关闭本地传输，未发布该助手话轮。此场景和其他测试均为本地替身，不证明实际网络事件顺序、供应商取消成功、远端停止或费用结算；回复若在本地通道关闭前一直没有到达，仍没有可靠取消或退出证据。当前不改变默认关闭的语音准入。供应商[客户端事件文档](https://help.aliyun.com/en/model-studio/client-events)说明对没有正在生成的回复执行取消会返回错误，因此不在尚无创建事件时猜测提前取消。

## WebRTC 多通道绑定修补

用户转述阿里云回复为“问题较复杂，正在核查”，并提供[实时交互](https://help.aliyun.com/zh/model-studio/omni-realtime-interaction-process)及[WebRTC接入](https://help.aliyun.com/zh/model-studio/realtime-webrtc-access)两份文档；两条原始 docs.bailian 链接本轮抓取超时，上述同标题官方帮助页可读。此回复未确认工单中的五项问题。WebRTC指南指出服务端会通过 `txt` 通道发送事件，并示例沿收到 `session.created` 的通道配置。

对照发现候选原实现将第一个打开的通道直接当作唯一事件通道，再打开另一通道就失败；同时打开客户端与服务端通道的协议单测和真实媒体控制器配替身传输测试均先失败。现允许最多8个已打开通道，以首个合法 `session.created` 所在已打开通道绑定会话并在同通道发送配置；其他打开但空闲的通道不导致失败，绑定后跨通道事件、未打开通道、初始化前业务事件或超限仍失败封闭。原来严格的 tools、搜索及其他配置回显门保持不变。验证是本地替身及已有真实事件的模拟安全字段重放，尚未在真实供应商 WebRTC 上运行修改后的 Dart 协议。
