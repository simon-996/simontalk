# WebRTC 远端音轨绑定修复

2026-10-30。真实千问单轮中，RTP 已到达但播放器仍显示 waiting。随后不再调用模型，在 Edge/macOS 建立本地双 PeerConnection 回环：合成静音上行，远端约 6.5 秒后加入合成音调轨，输出音频元素静音，不使用物理麦克风或设备扬声器。

旧脚本在创建播放器时先绑定空的 `MediaStream`。一次本地对照中，延迟音轨已启用、未静音且接收 250 包/20,188 字节，播放器仍 readyState 0、currentTime 0、无 `playing`；即使把元素挂到页面也如此。临时在音轨加入后重绑流，同一类回环出现 `playing` 和 readyState 4。以上仅说明所测 Edge 的现象，不推断其他浏览器的行为。

生产脚本改为先加入首条远端音轨再首次绑定流；媒体流绑定或加入失败时释放相关音轨及本地连接。新增两项 Node 测试分别先失败，修复后通过。最终脚本重新运行本地回环，未将音频元素挂到页面：延迟音轨到来后接收 250 包/20,188 字节，播放器 readyState 4、currentTime 约 11.51 秒，观察到 `playing`，资源随后关闭。源码与页面加载副本 SHA-256 一致。各次页面输出人工转录见[证据](evidence/2026-10-30-webrtc-audio-stream-binding.json)。

`playing` 在远端音调加入之前就已观察到，输出也始终静音，因而它不证明人耳听见、实际播放了哪一段或文字已对齐。本轮的真实千问控制器实验使用的是**修复前**脚本；修复后的生产脚本尚未在真实千问连接中重测。自然多轮、插话、可信远端退出、正式页面和业务后端仍未验证，正式语音准入保持关闭。

最终 Web Node 全量 77 项通过，Web release 构建通过；源码、浏览器实验副本和构建产物中的脚本 SHA-256 均为 `17bef89ce4a62acbcc8557464f9514656d411694b8d91366585eea949bad13e5`。本次只修改 JavaScript 和其测试，未重跑无关 Flutter 全量；此前 Flutter 结果见交接。
